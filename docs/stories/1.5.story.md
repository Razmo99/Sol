### Story

**As a Developer,** I want to take the newly migrated `New-CompanyUser` function (which now uses MS Graph) and refactor its logic into a new `NewUser-Builder` class, **so that** the feature is fully integrated into the new, extensible framework.

### Acceptance Criteria

1. The existing `New-CompanyUser` function logic is refactored into a new `NewUser-Builder` class that follows the established builder pattern.
2. The builder class integrates properly with the central `BuilderFactory` for operation selection and instantiation.
3. The refactored functionality maintains equivalent behavior to the migrated `New-CompanyUser` function while using the new class-based architecture.
4. All Microsoft Graph API calls and error handling patterns from the migrated function are preserved in the builder implementation.
5. The implementation follows all established coding standards, testing patterns, and project structure requirements.

### Dev Notes

#### Previous Story Insights
- The `New-CompanyUser` function has been successfully migrated to use Microsoft Graph API, replacing all legacy `AzureAD` and `MSOnline` cmdlets with their Graph equivalents. [Source: docs/stories/1.4.story.md]
- All Microsoft Graph patterns are established including connection management (`Connect-MgGraph`), user operations (`Get-MgUser`, `Update-MgUser`), and license management (`Get-MgSubscribedSku`, `Set-MgUserLicense`). [Source: docs/stories/1.4.story.md#Microsoft.Graph Migration Mappings]
- Robust error handling with try-catch blocks and logging module integration is already implemented. [Source: docs/stories/1.4.story.md#Completion Notes]
- MFA functionality has been removed from the codebase as part of the migration. [Source: docs/stories/1.4.story.md#Completion Notes]

#### Builder Pattern Architecture
- The module implements an extensible framework built on Builder Pattern (specific tasks encapsulated in Builder classes) and Factory Pattern (central Factory for selecting correct Builder). [Source: docs/architecture/2-proposed-architectural-vision.md#2.2]
- Abstract base class `TaskBase` defines the contract for all tasks with required `Invoke()` method and optional `Validate()` and `CheckPermissions()` methods. [Source: docs/architecture/component-design.md#1]
- Core class structure follows "fail-fast" philosophy with strongly-typed objects. [Source: docs/architecture/component-design.md#1]

#### Required Context Classes
- **SolUser**: Strongly-typed object for user being processed [Source: docs/architecture/component-design.md#SolUser]
- **TaskContext**: Rich context object with strongly-typed user object [Source: docs/architecture/component-design.md#TaskContext] 
- **TaskResult**: Standardized output from every task [Source: docs/architecture/component-design.md#TaskResult]
- **SolConfig**: Environment/session configuration [Source: docs/architecture/component-design.md#SolConfig]

#### File Locations and Structure
- **Builder Classes**: Located in `/Classes/Tasks/` following modulebuilder pattern [Source: docs/architecture/source-tree.md#/Tasks/]
- **Core Framework Classes**: Located in `/Classes/Core/` [Source: docs/architecture/source-tree.md#Core]
- **Factory Classes**: Located in `/Classes/Factories/WorkflowFactory.ps1` [Source: docs/architecture/source-tree.md#Factories]
- **Naming Convention**: Use `PascalCase` for classes, follow existing task naming patterns like `NewADUserTask.ps1` [Source: docs/architecture/coding-standards.md#Naming Conventions]

#### Microsoft Graph Integration Requirements
- **Required Scopes**: `User.ReadWrite.All`, `Directory.Read.All`, `Organization.Read.All` [Source: docs/stories/1.4.story.md#Required Graph Permissions]
- **Connection Pattern**: Use `Connect-MgGraph` with appropriate scopes [Source: docs/stories/1.4.story.md#Microsoft.Graph Migration Mappings]
- **User Operations**: `Get-MgUser -UserId $UPN`, `Update-MgUser -UserId $UPN -UsageLocation $Country` [Source: docs/stories/1.4.story.md#Microsoft.Graph Migration Mappings]
- **License Management**: `Get-MgSubscribedSku`, `Set-MgUserLicense -UserId $UPN -AddLicenses $addLicenses -RemoveLicenses @()` [Source: docs/stories/1.4.story.md#Microsoft.Graph Migration Mappings]

#### Technical Constraints and Standards
- **Strong Typing**: Use strong typing with `[OutputType]` attributes, include `using namespace` statements for .NET types [Source: docs/architecture/coding-standards.md#Coding Standards]
- **Collection Types**: Internal functions use `System.Collections.Generic.List[T]`, public functions accept/return standard PowerShell arrays [Source: docs/architecture/coding-standards.md#Collection Types]
- **Error Handling**: Preserve all try-catch blocks and logging module integration from migrated function [Source: docs/stories/1.4.story.md#Completion Notes]
- **Dependencies**: PowerShell 5.1+, Logging module, Microsoft Graph PowerShell Module [Source: docs/architecture/tech-stack.md]

#### Code Quality Requirements
- Avoid code smells: no `+=` in loops, no aliases, no `Write-Host`, no hardcoded config, no `Invoke-Expression` [Source: docs/architecture/coding-standards.md#Code Smells to Avoid]
- All functions and classes must include Pester-compatible, comment-based help [Source: docs/architecture/coding-standards.md#Documentation Standards]
- Follow modulebuilder file structure and organization [Source: docs/architecture/coding-standards.md#File Structure Approach]

#### Testing

**Testing Strategy**: Focus on framework logic, factory pattern, and command construction verification. Mock final cmdlet calls without execution. [Source: docs/prd/3-technical-constraints-and-integration-requirements.md#Testing Integration Strategy]

**Test Requirements**:
- **Mock Strategy**: Mock Microsoft Graph cmdlets (`Connect-MgGraph`, `Get-MgUser`, `Set-MgUserLicense`, etc.) to verify correct command construction and parameters [Source: docs/prd/3-technical-constraints-and-integration-requirements.md#Testing Integration Strategy]
- **Framework Testing**: Test builder pattern logic, factory integration, and task instantiation [Source: docs/prd/2-requirements.md#NFR6]
- **Validation Focus**: Verify correct command construction, parameter passing, and builder selection without executing platform-specific cmdlets [Source: docs/prd/2-requirements.md#NFR6]
- **Test File Location**: Following modulebuilder pattern, tests should be organized appropriately within the project structure [Source: docs/architecture/coding-standards.md#File Structure Approach]
- **Pester Framework**: Use Pester for all testing with mock strategies for external dependencies [Source: docs/prd/3-technical-constraints-and-integration-requirements.md#Testing Integration Strategy]

**Extensibility Validation**: The Definition of Done requires implementing at least two concrete "builders" to prove the extensibility pattern works as designed. [Source: docs/prd/3-technical-constraints-and-integration-requirements.md#QA]
